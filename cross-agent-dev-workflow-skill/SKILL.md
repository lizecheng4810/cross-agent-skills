# Skill: cross-agent-dev-workflow-skill（项目交付总流程 · 三位一体之总调度）

## 这个技能是什么

一套让任何 Agent / Harness **从需求走到「可上线发布」的总流程协议**。它把用户手写的重流程提示词（深度研发迭代 / 深度测试纠错 / 深度整理发布 / 全程挂载记忆与脚本治理）固化成**证据制、可中断续跑、有停止闸**的阶段协议。

**三位一体定位（本技能与两个伙伴密不可分）：**

| 技能 | 角色 | 职责 |
|---|---|---|
| `cross-agent-memory` | **大脑** | 记什么：分层记忆、踩坑、偏好、决策、待办（知识沉淀） |
| `cross-agent-scratchpad-skill` | **清洁工** | 管脚本：临时脚本建在哪、复用、何时删、遗留物分级处置 |
| 本技能 `cross-agent-dev-workflow-skill` | **总调度** | 定流程：当前在哪个阶段、验收门过没过、何时必须停、状态存哪 |

> 一句话：**memory 记账、scratchpad 打扫、dev-workflow 掌舵。** 本技能不替代两个伙伴，而是驱动它们、被它们承载——阶段状态就存在 memory 的 `5_代办.md` 里，删除操作就委托 scratchpad 的分级协议。

## 零、强制总则（四条，凌驾于所有阶段之上）

### 总则 1 · 规模分档（防小任务套重流程）

接手任务先定档位，只执行所触达阶段的协议，**不得对小任务全量硬跑**：

| 档位 | 判定 | 走法 |
|---|---|---|
| **轻量** | 单点小改、问答、微调 | 阶段0 照走（读记忆/状态）→ 直接干活 → 收尾更新记忆。不启动研发/测纠全协议 |
| **标准** | 常规功能开发、局部重构 | 阶段0 → 触达的阶段（如只走研发）→ 对应验收门 |
| **深度** | 新项目、大改、或用户明确说「ultrathink / 深度研究 / 全网搜索 / 迭代到可上线发布 / 整理发布」 | 阶段0 → 1 → 2 → 3 全量，逐阶段过验收门 |

### 总则 2 · 证据制验收门

- 每个阶段有 DoD 清单（模板见 `references/验收清单.md`，复制到项目后逐项打勾）。
- 「完成」「没问题」「可上线发布」的操作定义：**已知问题清单为空（或全部是用户已知悉的接受项）+ 本阶段验收清单全过 + 每项有证据**（命令输出、文件直链、审查记录）。
- 禁止纯自评式宣布完成：自己写的自己测天然偏松，必须用清单+证据压制（深度档建议换一个未参与编写的子 Agent 复审）。

### 总则 3 · 停止闸（防过度打磨）

- **验收门一过就停**：向用户报告「已达可上线发布状态」，然后停手，不做清单外的额外优化、不加未要求的功能、不继续重构。
- 用户原话精神：达到预期后「不要再做更多多余的事情」。多做的每一件事都是新的风险面。
- 报告格式（结论先行）：`已达到 X 状态。依据：验收清单 N/N 全过（证据：…）。已知接受项：…。`

### 总则 4 · 方向拍板与权限降级

- **用户拍板线**：架构选型、对外接口、不可逆操作（删除/覆盖/发布/对外发送）、超出原需求范围的想法 → 先给方案+推荐+风险，等用户决断（「有想法思路大家一起研究讨论」）。
- **权限降级**：会话权限受限（无法联网/无法装软件/命令被拒）时，**优雅降级**——改用本地可行路径、如实报告受限项，绝不因权限不足而硬闯或静默跳过验收。
- **安装位置协议**：经授权需要下载安装软件/技能/插件/扩展时，装到用户指定的「软件安装位」（查工作区记忆/本机配置；示例：`D:\Agent下载`，文件夹不存在则先创建）；未指定时**先询问用户**，绝不散装乱放——设备级路径不写死在本技能里（可移植性）。
- **删除红线**：任何阶段需要删文件，一律走 scratchpad 的分级处置协议（复用→迁入 / 无价值→记录后清理 / 来源不明→隔离+等确认），真实工程文件绝不自动删。

## 一、阶段 0 · 接手（与三位一体伙伴共用入口）

**每次接手任务的强制第一步**（与 memory / scratchpad 的接手协议是同一个入口，一次深读服务三者）：

1. **一键接手**（有 Python 时）：`python 工具\记忆管家.py 接手 <工作区>`（记忆扫描 + 分层完整性 + 并发校验 + 临时脚本库配置联动检查）。
2. **手工等价**（无 Python 时）：
   - 读根记忆层 `0_索引`（先看「分层方案」）→ 深读记忆文件；没有记忆 → 深读整个项目；
   - 读本机配置 `~/.agent-tsg/config.json`（scratchpad：临时脚本库路径，未配置先问用户）；
   - 记忆无「已审计」标记 → 做/补遗留物审计（scratchpad 节点1）。
3. **读取交付流程状态**：看记忆 `5_代办.md` 的「🚦 交付流程状态」段（格式见 §五）→ 有状态则**从断点续跑**（不重复已完成阶段），无状态则按总则 1 定档位、从阶段 1 起步。
4. **校验前提**：检查用户提问中的错误前提、逻辑跳跃、信息缺失——发现直接指出，不带错硬做。

---

## 二、阶段 1 · 研发迭代（深度研究 → 资产检索 → 方案 → 多轮实现）

> 完整细则见 `references/阶段一_研发.md`。骨架：

1. **深度研究理解**：读透项目与记忆，把用户的验收期望翻译成可核查的验收清单（写入项目，供阶段 2/3 复用）。
2. **资产检索**（深度档必做）：GitHub 深度检索可复用/可二开仓库；联网查论文、他人成果、最佳实践。**复用优先于自造**；选型结论（候选/推荐/弃用理由）记入 `决策.md`。
3. **方案设计**：至少 1 个候选方案 + 推荐 + 风险 + 隐性成本；跨过总则 4 拍板线的，先请用户决断。
4. **实现与多轮迭代**：每轮 = 小步实现 → 自测 → 记录（进度入 `5_代办`、坑入 `2_踩坑日志`、偏好入 `3_个性化需求`）；需要临时脚本 → 一律外部库（scratchpad 节点2）。
5. **阶段验收门**：功能达成 + 方案落地 + 记录完整 + 无未披露假设 → 状态转移入 `5_代办`，进入阶段 2。

**防跑偏**：检索有时间与轮次上限意识（连续数轮无增量即收）；复用不硬凑（改造成本 > 自造成本时如实记录并放弃）。

---

## 三、阶段 2 · 测试纠错（实际运行 → 逐文件审查 → 纠错循环）

> 完整细则见 `references/阶段二_测纠.md`。骨架：

1. **实际运行测试**：真跑（真实命令、真实环境、真实数据样本）；跑不了的必须写明原因与替代验证手段。
2. **逐文件深度审查**：全量文件清单化，逐个过（OK / 问题+根因）；不抽样、不跳过声明「没看」的文件。
3. **纠错循环**：每轮记录 问题 → 根因 → 修复 → 验证；**回归检查**（修 A 不能坏 B）。
4. **证据制验收门**（总则 2）：已知问题清单为空 + 验收清单全过 + 测试输出留证 → 状态转移，进入阶段 3。
5. 发现设计级问题（不是实现缺陷）→ 回阶段 1，状态机如实记录回退。

---

## 四、阶段 3 · 整理发布（结构整合 → 遗留物处置 → 打包 → 发布清单）

> 完整细则见 `references/阶段三_整理发布.md`。骨架：

1. **结构整合**：深读全部文件后合并冗余、统一命名与文档口径（同一事实一个出处）；文档多处提到同一机制时必须同步改（口径漂移是本套件历史踩过的坑）。
2. **遗留物处置**：委托 scratchpad 分级协议（A 自己的 / B 复用迁入 / C 无价值记录后清理 / D 来源不明隔离+等确认）；旧版本文件交给 git 历史归档，工作区只留当前所需。
3. **发布打包**：版本与变更记录、zip 打包（用 `工具\发布管家.py 打包`，自动排除 `__pycache__`/`.pyc`/记忆文件夹）、README 与安装指引核对、license 在位。
4. **发布清单全过** → 按总则 3 报告「已达到可上线发布状态」→ 停手。
5. **发布后收尾**：记忆更新（`0_索引` 日志、`5_代办` 清到下一周期、必要时写 `交接简报.md`）、本次脚本处置（scratchpad 节点3）。

## 五、阶段状态机（跨会话 / 跨 Agent 续跑）

**当前阶段与证据存在记忆 `5_代办.md` 的固定段**（没有 memory 技能时的降级见 §六）：

```markdown
## 🚦 交付流程状态（cross-agent-dev-workflow 维护）
- 档位：轻量 / 标准 / 深度
- 当前阶段：阶段1-研发 / 阶段2-测纠 / 阶段3-整理发布 / 已达发布态
- 本轮进度：<一两句话>
- 验收证据：<直链清单/测试输出/审查记录>
- [YYYY-MM-DD] [署名] 阶段转移：阶段X→阶段Y，依据：<验收门结果摘要>
```

- **转移规则**：只能 向前（1→2→3）或 如实回退（2→1 设计级问题）；每次转移追加一行，不改写历史行。
- **续跑规则**：接手 Agent 看到本段即知断点，从对应阶段继续，**不重复已过验收门的工作**。
- 更新本段遵守 memory 的「写前三步：先读→合并→写回」。

## 六、三位一体联动（与两个伙伴的协作总图）

| 阶段 | 本技能调用 memory（大脑） | 本技能调用 scratchpad（清洁工） |
|---|---|---|
| 阶段0 接手 | 读 0_索引/分层方案/5_代办状态段；无记忆深读项目后建层 | 共用接手入口；遗留物审计（增量） |
| 阶段1 研发 | 决策入 `决策.md`；坑入 `2_踩坑日志`；进度入 `5_代办` | 临时脚本先查库复用、建在外部库 |
| 阶段2 测纠 | 缺陷与根因入 `2_踩坑日志`；验收证据入 `5_代办` 状态段 | 测试脚本是临时脚本，同上治理 |
| 阶段3 发布 | 文档口径/结构变化入 `1_项目架构`；收尾日志入 `0_索引` | 遗留物分级处置；本次脚本收编/清理 |
| 全程 | 阶段状态机就存在 `5_代办.md` | 一切删除走其分级红线 |

- 双向联动细节：`联动/cross-agent-memory.md`、`联动/cross-agent-scratchpad.md`（本技能写什么/读什么，逐文件列表）。
- **伙伴未安装时的降级（三条铁律）**：① 至少在工作区维护一个 `交付状态.md`（按 §五格式）承载状态机；② 临时脚本绝不落在项目工作区；③ 删除操作一律先问用户。

## 七、工具脚本（可选兜底）

主工具 `工具/发布管家.py`（Python 3.8+，跨平台，无第三方依赖）：

| 命令 | 作用 |
|---|---|
| `校验技能 <技能目录>` | 按 Agent Skills 规范校验 SKILL.md（name/description 规则、行数、引用文件在位） |
| `三位一体 <套件根>` | 校验三技能互链对称（联动文档双向在位、SKILL.md 互提） |
| `打包 <技能目录> [--out <zip>]` | 打发布 zip（自动排除 `__pycache__`/`.pyc`/`记忆第*层`/`记忆_通用`/`.git`） |
| `发布检查 <套件根>` | 发布前总检：zip 新鲜度（源文件晚于 zip 即报 stale）、README 覆盖、LICENSE 在位、ship 清单预览 |

`工具/发布管家.ps1` 为 Windows 薄封装（转发到 Python）。**工具不是必须的**——没有 Python 时按本协议手工执行完全成立。

## 八、诚实边界（强制使用的边界声明）

- 本技能通过协议强约束**加载了它的 Agent/Harness**；无法强制未安装的第三方工具。
- 技能移植的是**指令**，不是**能力**：不同 harness 的工具集（联网搜索、子 Agent、权限模式）不同，执行时按实际能力降级并如实报告（总则 4）。
- 证据制验收门能**压制**自评偏差，不能清零：深度档建议由未参与编写的子 Agent 复审，用户保留最终裁决权。

## 关键原则

1. **三阶段流水线**：研发 → 测纠 → 整理发布，每阶段独立验收门，可单独触达（配合规模分档）。
2. **三位一体**：memory 记账、scratchpad 打扫、本技能掌舵；状态机存记忆，删除走分级红线，接手共用一个入口。
3. **证据制**：「没问题」= 已知问题清单为空 + 验收清单全过 + 有证据，不接受纯自评。
4. **停止闸**：验收门一过即停，不做多余的事。
5. **可续跑**：阶段状态入记忆，任何 Agent 任何设备从断点继续。
6. **用户拍板线**：重大方向、不可逆操作，先讨论后动手。

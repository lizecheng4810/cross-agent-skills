# 阶段 3 · 整理发布（细则）

> 前置：阶段 2 验收门已过。本阶段目标：**从「没有已知问题」走到「结构最佳、可打包分发、报告可上线」**。
> 本阶段动作多涉及删除/移动/重命名——**一切删除走 scratchpad 分级红线**，真实工程文件绝不自动删。

## 3.1 结构整合

1. **深读全部文件**后做判断（不是按文件名猜）：
   - 合并冗余：同一信息多处维护的，收敛到「一个事实一个出处」，其余改为直链/引用。
   - 统一命名与口径：文件命名风格、术语、文档表述一致。
   - **口径同步**（本套件历史踩过的坑）：同一机制在 SKILL.md / README / 安装指引 / 工具注释等多处出现时，改一处必须同步所有处——发布前逐处核对。
2. 判定为「旧迭代遗留」的文件/结构 → 进 3.2 分级处置，不直接删。
3. 结构变化写入记忆 `1_项目架构.md`（先读→合并→写回）。

## 3.2 遗留物处置（委托 scratchpad 分级协议）

| 分类 | 判定特征 | 动作 |
|---|---|---|
| A. 本次会话产物 | 本轮任务创建 | 该归档归档（git 提交/reports），临时脚本按 scratchpad 节点 3 处置 |
| B. 历史遗留、有复用价值 | 临时脚本特征 + 用途可辨识 | 迁入外部库 `reusable/` 并登记元数据 |
| C. 历史遗留、无价值 | 用途失效/与项目无关/纯重复 | **写入审计记录后**清理（优先回收站）；git 已跟踪的靠 git 历史兜底 |
| D. 来源不明 / 拿不准 | 正式命名但无引用、判断没把握 | **只隔离 + 报告 + 等用户确认**，列入记忆 `6_需要我配合.txt` |

- 处置全程留痕：每项「保留/迁移/删除」的依据与结果记入 `决策.md` + 外部库 `reports/`。
- **版本管理兜底原则**：旧版本文件的工作区副本删除前确认 git 历史已有（或先提交再删），保证可恢复。

## 3.3 发布打包

1. **版本与变更**：确定版本号（语义化或套件既有习惯），变更记录写入 CHANGELOG / README 对应段。
2. **zip 打包**：`python 工具\发布管家.py 打包 <技能目录>`（自动排除 `__pycache__`/`.pyc`/`记忆第*层`/`记忆_通用`/`.git`）；打完 `发布检查` 确认新鲜度。
3. **文档核对**：README 覆盖全部交付物、安装指引可用（目录矩阵与实际一致）、license 在位、对外链接有效。
4. **发布检查总检**：`python 工具\发布管家.py 发布检查 <套件根>`——zip stale、README 缺项、LICENSE 缺失、ship 清单里的意外文件，全部清零或确认为有意保留。

## 3.4 发布清单（全过才算「可上线发布」）

| # | 检查项 | 证据 |
|---|---|---|
| 1 | 阶段 2 验收门结论仍成立（整理过程未引入新问题；如有改动，重验受影响项） | 重验记录 |
| 2 | 结构整合完成：无未处置遗留物（D 类已列入待确认清单） | 处置清单 |
| 3 | 口径同步：多处文档关于同一机制的表述一致 | 逐处核对记录 |
| 4 | 打包完成且新鲜（zip 晚于全部源文件） | `发布检查` 输出 |
| 5 | 安装指引按新包实测过一遍（或声明沿用已验证路径） | 安装验证记录 |
| 6 | 已知问题清单（应为空或全为用户接受项） | 清单 |

→ 全过：按总则 3 报告并**停手**：

```
已达到可上线发布状态。依据：发布清单 6/6 全过（证据：…）。
已知接受项：…（无则写「无」）。
```

## 3.5 发布后收尾（与两位伙伴合并执行）

- 记忆：`0_索引.md` 更新日志追加一条；`5_代办.md` 状态段置为「已达发布态」并把待办清到下一周期；结构/口径变化入 `1_项目架构.md`；需要交接时写 `交接简报.md`。
- 脚本：本次临时脚本按 scratchpad 节点 3 收编/清理/隔离。
- 不做的事：发布清单之外的「顺手优化」——那是下一周期的事（总则 3 停止闸）。

## 常见跑偏与对策

| 跑偏 | 对策 |
|---|---|
| 整理时手滑删错 | 一切删除走 3.2 分级 + git 兜底 + D 类等确认 |
| 文档口径漏同步 | 3.1 第 3 条逐处核对 |
| zip 忘了重打（改了源没打包） | `发布检查` 新鲜度校验 |
| 发布后又想顺手改 | 停止闸：清单外事项记入 `5_代办` 下一周期 |

# 跨 Agent / 跨 Harness 就地记忆技能

## 这个技能是什么

一套**让任何 Agent 或 Harness 在任何真实工作区里就地沉淀并继承记忆**的协议。核心思想：**记忆不是集中放在某个"记忆库"，而是直接嵌在工作区自己的文件夹树里，随工作区走。**

**核心要求（最重要）：**
1. **就地嵌入**：记忆文件夹直接建在真实工作区/项目的文件夹树里，命名带层级（`记忆第一层`/`记忆第二层`/`记忆第三层`/`记忆第四层`……），每个文件夹含 `0_索引.md` + 完整 **6 件**。
2. **层数由 Agent 深度研究后自主决定（1~N 层，不设上限）**：首次接手一个工作区时，**必须独立深度研究、分析、判断**项目的真实结构，自主决定该分几层、每层对应哪个文件夹、每层记什么——**不是固定三层**。简单项目可以只有一层，复杂多级工程可以四层、五层甚至更多。结论写成「**分层方案**」记入根记忆层 `0_索引`，后续 Agent 遵循。
3. **Agent 自主判断 + 深度理解后填写**：深度阅读并理解工作区里的全部项目文件，融合对话经验记忆，按分层方案**自己归纳总结项目知识，填入记忆文件**（不是拷贝空模板了事）。
4. **每次对话/任务后实时更新，写前三步：先读→合并→写回**：装了这个 skill 后，**每次执行任务、或每次对话结束，都更新记忆**——更新前**必须先深度阅读该层现有记忆**（因为可能已被其他 Agent/Harness 写入过，可用 `记忆索引.json` 指纹校验辅助检测），**在原有内容基础上修改、合并、优化，绝不覆盖/清空**。
5. **接手任务先读记忆（强制）**：只要装了本 skill，接手任何工作任务时**第一步必须先读根记忆层 `0_索引`（先看「分层方案」），再深度阅读项目/工作区里的记忆文件**；如果没有记忆文件，则**深度阅读整个项目文件**后按第 2 条自主定层。有记忆先读记忆，没记忆读整个项目。
6. **层级完整性检查（主动补齐新增记忆层）**：每次使用本技能都要**递归扫描工作区**，对照分层方案找出新增的模块/子工程文件夹（**任意深度**）；对缺记忆层的，**立即主动按记忆层级序数补齐对应 `记忆第X层`（建 6 件 + 深度理解后填写），不等用户提醒**。
7. **每次任务都用**：装了这个 skill 后，**执行任何任务都必须使用本技能**——工作区没有记忆文件夹，就深度阅读后按研究结论定层、添加；已有记忆文件夹，每次对话/任务后更新。

## 一、记忆文件夹在哪：就地嵌入，层号 = 记忆层级序数

以工作区 `D:\AAA实习\新闻爬虫` 为例（本工作区 Agent 研究后决定分 4 层）：

```
D:\AAA实习\新闻爬虫\                    ← 第一层（工作区 / 所有任务通用）
│   └── 记忆第一层\（6件）
│
├── 爬取新闻\                           ← 第二层（相近/相关任务类）
│   ├── 记忆第二层\（6件）
│   └── AI_NEWS_MARKETS\
│       ├── CHINA\                      ← 第三层（单项目模块）
│       │   └── 记忆第三层\（6件）
│       ├── WORLD\                      ← 第三层（单项目模块）
│       │   └── 记忆第三层\（6件）
│       └── LEGACY\                     ← 第三层（老系统值得单独记，所以 LEGACY 也建层）
│           ├── 记忆第三层\（6件）
│           └── 老系统\                 ← 第四层（因为 LEGACY 已占第三层）
│               └── 记忆第四层\（6件）
```

**命名规则**：**层号 = 记忆层级序数**——根是第一层；某文件夹的层号 = 根到它的路径上**拥有记忆层的祖先数 + 1**。分组文件夹（如 `AI_NEWS_MARKETS`、`platforms`）自己不建记忆层就不占层号，模块层号不会被分组层级虚增。层号用中文数字（一/二/三/四/……/九十九）。工具按此推断和校验，Agent 建层时也遵守，保证跨 Agent 一致、不会各自发明层数。

**每层都放 `0_索引` + 完整 6 件**：

| # | 文件 | 记录内容 |
|---|---|---|
| 0 | `0_索引.md` | 本层速览（≤60 行）：六件各一句话 + 关键事实直链 + 追加式更新日志 + 「🔗 通用知识」段（引用 `<工作区>/记忆_通用/`）。**根记忆层的 0_索引 还要记「分层方案」**（见下）。**接手 Agent 先读本页** |
| 1 | `1_项目架构.md` | 该层结构、模块作用、模块如何配合 |
| 2 | `2_踩坑日志.md` | 踩过的坑：问题/原因/解决/影响范围 |
| 3 | `3_个性化需求.md` | 命名、注释、字段等偏好（下层覆盖上层用 ⚠️ 标注） |
| 4 | `4_提示词配方.md` | 好的提示词模板；差需求的诊断+重写模板 |
| 5 | `5_代办.md` | 进行到哪一步、下一步、下一个坑 |
| 6 | `6_需要我配合.txt` | 需要用户补充/配合，按重要性排序 |

> 可选扩展：`决策.md`（已确认的需求/澄清）、`交接简报.md`（接手主入口）、`工具环境.md`（可用工具/技能/约束）。
> 每层文件夹里还有一份 `记忆索引.json`（指纹档案，由工具维护），记录各记忆文件的 sha256/mtime/更新者，用于并发检测——**Agent 不手工编辑它**。

### 「分层方案」（记在根记忆层 0_索引，跨 Agent 的分层契约）

首次定层（或结构变化修订）后，在**根记忆层 `0_索引.md`** 里维护一小节：

```
## 分层方案（共 N 层）
- 第一层 = <工作区根>：记 <职责一句话>
- 第二层 = <爬取新闻>：记 <职责一句话>
- 第三层 = <AI_NEWS_MARKETS 下各模块>：记 <职责一句话>
- 第四层 = <……/LEGACY/老系统>：记 <职责一句话>
- [YYYY-MM-DD] [署名] 定层依据：<为什么这么分，一两句>
```

作用：后续任何 Agent 接手时**先读这一节**，按既定层数与职责维护记忆，而不是重新发明一套分层；结构变化时修订此节并追加日志。

## 二、如何决定分几层（Agent 独立深度研究分析判断 · 1~N 层不设上限）

**层数不是规定出来的，是研究出来的。** 首次使用一个工作区（或遇到不熟悉的工作区）时：

### 第 1 步：深度阅读
通读工作区里的目录树、代码、README、文档、脚本、数据文件、配置，理解：
- 有几级真实的组织结构（工作区 → 任务类 → 项目 → 模块 → 平台 → …）；
- 每一级是否承载**不同粒度、可复用的知识**（通用偏好 / 任务类经验 / 单项目细节 / 子模块细节）。

### 第 2 步：独立研究分析判断层数 N（不是最多三层）
对每一级结构问自己：
- **这一级的知识是否和上下级不同**（若完全相同 → 合并，不建层）；
- **接手 Agent 会不会在这一级需要独立上下文**（会 → 建层）；
- **记忆量是否会大到需要单独一页索引**（会 → 建层）。

判断结论允许任何层数：
- **1 层**：单一平铺的小项目，全部知识放根记忆层即可；
- **2 层**：工作区 + 项目两级；
- **3 层**：经典的工作区 / 任务类 / 单项目；
- **4 层及以上**：多级工程（如 工作区 / 平台矩阵 / 单平台工程 / 平台内子模块），按真实结构延伸，**不设上限、也不为凑数硬造**。

原则：**每层都要有独立存在的理由——宁可少而准，不为形式硬造；但该深的层级不要偷懒合并。**

### 第 3 步：定层 + 落盘
1. 确定 N、每层对应的文件夹、每层职责；
2. 就地在每层文件夹里创建对应的 `记忆第X层`（层号 = 记忆层级序数）；
3. 把「分层方案」写进根记忆层 `0_索引`（格式见上）；
4. 深度理解 + 融合对话经验后填写各层 6 件。

> 兼容说明：早期版本固定一/二/三层，已有工作区的 `记忆第一层`/`记忆第二层`/`记忆第三层` 命名不变、继续沿用；接手时若发现现行分层方案层数更多，按本节研究后修订分层方案、补建更深层即可，**不重命名旧层**。

## 二·五、层级完整性检查（最重要 · 每次都要主动做）

> ⚠️ **这是最容易漏、也最常被抱怨的一步。** 项目结构会**变化**（新增子工程、模块、平台文件夹，且可能在任意深度）。出现新的候选文件夹时，**必须按分层方案主动为它建立对应层号的记忆层**，不能只更新已有的记忆层。

**每次使用本技能（接手任务 / 对话结束 / 任务完成）时，都要做一次"层级完整性检查"：**

1. **递归扫描**当前工作区/工程（对照根层 `0_索引` 的「分层方案」），找出所有"应建记忆层的模块/子工程文件夹"及其应有层号（=记忆层级序数）。例如：`platforms/windows`、`modules/xxx`、`CHINA`、`WORLD`、各独立子工程、更深层子模块。
2. **对比检查**：对每个这样的文件夹，看它里面是否已有对应 `记忆第X层`。
   - **已有** → 进入更新流程（先深读，再在原基础上更新）。
   - **没有（缺失）** → **立即主动**建层（6 件）并**深度理解该模块后填写**——**不等用户提醒**。
   - 候选文件夹的层号超出分层方案现有层数 → 说明结构变深了，**先修订「分层方案」（追加日志），再建层**。
3. **同步确认上层**：从根层往下逐级确认齐全；缺失则一并补齐。
4. 检查后，在根层 `5_代办.md` 或更新日志里记录本次补齐了哪些新增记忆层。

> **判定哪些文件夹是"应建层"的模块**：能独立演进/独立构建/有自己独有壳或配置的工程、子项目、平台、模块目录。参考：平台工程（windows/macos/android/ios/harmonyos）、子项目、独立模块。**宁可多建，不可漏建**——漏了，接手 Agent 就看不到该模块的经验。

> **核心场景（务必覆盖）**：把一个大工程拆分成多个独立子工程/平台文件夹后，**每个子工程文件夹都要有记忆层**。日志中常见的错误是"只给上层工程建了层，忘了给拆分出来的各子工程/平台建层"。

## 三、如何填写记忆（0_索引 + 6 件：深度理解 + 融合对话经验）

**这是本技能最关键的环节。** 创建 `记忆第X层` 文件夹后，**必须深度理解该层的内容，用自己的分析归纳填写 `0_索引` 和 6 件**，而不是把模板拷过来留空。

### 信息来源：项目文件 + 对话经验记忆（两者融合）

填写 6 件时，**不能只读项目文件**，要同时深度结合**对话经验/上下文记忆**：

- **项目文件**：代码、README、文档、脚本、数据结构、命名规范等。
- **对话经验记忆（主）**：本次对话里你说过的话——需求、偏好、澄清、确认过的决策、踩过的坑、纠正过 Agent 的地方、你强调的注意点。
- **历史会话记忆（辅）**：若有可用的跨会话上下文/经验，作为辅助参考。

> 很多关键信息（命名/注释偏好、为什么这样设计、踩过的坑）**往往只存在于对话里，项目文件里没有**。所以必须把两者融合，才能写出真正有价值的记忆。

### 每个文件的来源（项目文件 + 对话经验）

| 文件 | 项目文件来源 | 对话经验来源 |
|---|---|---|
| **1_项目架构** | 模块/文件/依赖/数据流 | 你在对话里解释的设计意图、为什么这样拆分 |
| **2_踩坑日志** | 代码注释里的 TODO/坑 | 你反馈的报错、你指出的坑、AI 踩坑后你纠正的 |
| **3_个性化需求** | 代码里的命名/注释习惯 | **最主要来源**：你直接说的命名/注释/字段/风格偏好 |
| **4_提示词配方** | — | 你说"这个需求清楚/写得不好"时对话里确认的模板 |
| **5_代办** | 项目进度文件 | 对话里确认的下一步、你要求的优先级 |
| **6_需要我配合.txt** | — | 对话里你说"我需要你提供…"、你反问后记录的待补事项 |

填写要点：
- **1_项目架构**：归纳该层真正在做什么、有哪些模块/文件、它们怎么配合、数据怎么流。融合对话中你对设计的解释。写具体的，别写空话。
- **2_踩坑日志**：记录实际遇到的坑（问题/原因/解决/影响），包括你这次任务踩到的，以及对话中你反馈/纠正过的坑。
- **3_个性化需求**：从文件**和对话里**识别命名/注释/字段习惯；你亲口说的偏好是最高价值（若下层覆盖上层，标 `⚠️ 覆盖上层`）。
- **4_提示词配方**：沉淀对话里确认的"写得好"的需求模板；遇到差需求时记录诊断和重写模板。
- **5_代办**：当前进度、下一步、预估的坑（融合对话里你确认的下一步）。
- **6_需要我配合.txt**：列出需要用户补充/拍板/提供材料的事项，按重要性排序（来自对话）。

> 模板文件放在 skill 目录的 `_模板/` 下，作为**格式参考**，但内容是你要根据对项目的真实理解 + 对话经验来填写的。

## 四、何时使用 / 更新（每次对话/任务后都要实时更新）

**只要执行任务、或任何一次对话结束，就调用本技能更新记忆——几乎实时更新。**

### 接手工作任务时（启动必做，强制）

**只要装了本 skill，接手任何工作任务时，第一步必须：**

1. **先读根记忆层 `0_索引`**（先看「分层方案」了解本工作区分几层、每层职责），再深度阅读相关层的记忆文件（尤其 `5_代办`、`6_需要我配合`、`1_项目架构`、`3_个性化需求`、`4_提示词配方`）。
2. **如果没有记忆文件** → **深度阅读整个项目文件**，按「二」的研究方法**独立判断层数**后建层。
3. 据此理解上下文后，再开始执行任务；并在任务/对话过程中按下面的更新协议实时维护记忆。

> 一句话：**有记忆先读记忆（先看分层方案），没记忆就研究整个项目自主定层。** 这是每次接手任务的强制第一步，不能跳过。

### 更新前必做：深度阅读现有记忆 + 并发校验（最重要）

因为这是**跨 Agent / 跨 Harness** 的 skill：同一个任务、同一个工作区里，**可能同时有多个 Agent / Harness 在写入记忆文件**。所以每次更新前，**必须先深度、仔细地阅读该层现有的记忆文件**：

- 可能已被**其他 Agent/Harness** 在这期间写入、修改过内容。
- 要识别出：哪些已经更新过了、哪些是新的、哪些需要合并/修正。
- **在原有内容的基础上修改、更新、优化**——**绝不能直接覆盖/清空**，否则会抹掉别人刚写入的记忆。

> 核心原则：**「写前三步：先读 → 合并 → 写回。」** 更新 = 在现有基础上增补、合并、修正，而不是重写。

**并发安全强化（借鉴 append-only journal + hash 校验模式）：**

1. **更新方式以追加为主**：日志类内容（踩坑、更新日志、决策）一律**追加带日期+署名的新条目**（格式：`- [YYYY-MM-DD] [agent/harness名] 内容`），不改写别人的条目；只在事实变化时才修改旧条目原文并标注。
2. **指纹校验（可选辅助）**：各层 `记忆索引.json` 记录了上次更新时各文件的 sha256。更新前可用工具 `校验` 检测「自上次记录后是否有其他 Agent 改过文件」；检测到改动 → 先深读被改文件再合并；合并完成后用 `校验 --refresh`（或 `校验 --refresh --by <署名>`）刷新指纹。没有工具时，靠「先读再改」的纪律同样成立。
3. **一个事实一个出处**：同一信息不在多件里重复维护；跨文件只在本层 `0_索引` 放一句话直链。

**时效与衰减（防记忆无限膨胀，保持高信号）：**

- 每条重要记忆尽量带日期；定期整理（如结构大改、任务收尾）时：**失效条目删除或移入各文件末尾「已归档」小节**、重复条目合并、`0_索引` 的更新日志压缩为摘要。
- 整理也遵守「先读→合并→写回」，且整理动作本身在更新日志里记一条。

### 流程

1. **开始任务前（强制）**：定位所在工作区，**先做「层级完整性检查」**（见「二·五」）：
   - 递归扫描工作区，对照分层方案找出所有应建记忆层的模块/子工程文件夹（任意深度）。
   - 对每个这样的文件夹：**有对应记忆层 → 深读后更新；没有 → 立即主动补齐（建 0_索引 + 6 件 + 深度理解后填写）**。
   - 同时从根往下逐级确认齐全；缺失则一并补齐；层数变了先修订「分层方案」。
2. **读记忆/读项目**：查看是否已有记忆文件夹。
   - **没有** → 深度阅读工作区，按「二」独立研究判断层数 N，就地创建各层并填写 `0_索引` + 6 件 + 分层方案。
   - **有** → **先读根层 `0_索引`（分层方案），再深度阅读对应层其余记忆文件**；有指纹档案时可先 `校验` 检测外部改动。
3. **执行任务中 / 每次对话后**：
   - 踩到坑 → 立刻向该层 `2_踩坑日志.md` **追加**一条带日期+署名的条目。
   - 需求被确认/澄清 → 记入 `决策.md`（可选）或 `5_代办.md`。
   - 用户配合了新事项 → 更新 `6_需要我配合.txt`。
   - **结构变化（新增子工程/模块/平台文件夹）→ 按分层方案主动为新文件夹建对应层号的记忆层。**
4. **任务完成后 / 对话结束后**：**先深读现有记忆，再在原基础上更新**该层 `0_索引`（更新日志追加一条）、`5_代办.md`（已完成/下一步）、`1_项目架构.md`（结构变化）、`3_个性化需求.md`（新偏好）、`6_需要我配合.txt` 等；需要时刷新 `记忆索引.json` 指纹。**再做一次层级完整性检查**，确认没有遗漏新增模块。

> 重要：步骤 3、4 的每次更新，**都先读一次现有记忆**，确保不覆盖其他 Agent/Harness 刚写入的内容。

**读取顺序（接手时）**：先读根层 `0_索引`（分层方案）→ 本层 `0_索引` → `5_代办` → `6_需要我配合` → `1_项目架构` → `3_个性化需求` → `4_提示词配方` → `2_踩坑日志`；再向上读父层、根层（下层覆盖上层）。

## 五、分层原则（防漂移）

**一个事实只有一个权威出处。**
- 每一层只写**该层级粒度**的知识（根层=通用，越深越具体）——具体粒度以「分层方案」为准。
- 下层只写对上层的覆盖/补充，不复制上层内容。
- 下层覆盖上层时必须标注 `⚠️ 覆盖上层` / `补充上层`，避免同一信息多处重复。
- 相邻层职责重叠时，回头修订「分层方案」并记日志，而不是两处都写。

## 六、工具脚本（可选辅助）

主工具 `工具/记忆管家.py`（Python 3.8+，跨平台）。**层号约定 = 记忆层级序数（根=第一层），支持一~九十九层**：

| 命令 | 作用 |
|---|---|
| `接手 <工作区> [--by 署名]` | **一键接手入口**：记忆_通用 检查 + 扫描已有记忆层（任意层数）+ 层级完整性检查（缺层的候选）+ 各层并发校验 + 交付流程状态（🚦，cross-agent-dev-workflow）+ 临时脚本库配置联动检查。接手任务时先跑这一条 |
| `建层 <文件夹> --层 <层号>` | 就地建 `记忆第X层`（0_索引 + 6 件格式参考 + 初始指纹档案）。层号用中文数字（一/二/三/四…）或阿拉伯数字（1/2/3/4…），应等于记忆层级序数 |
| `建层 <工作区> --通用` | 就地建中央 `记忆_通用/`（0_通用索引 + 4 件 + 初始指纹档案）；`索引/校验` 也认 `--层 记忆_通用` |
| `扫描 <工作区>` | 列出工作区里已有的 `记忆第X层` 文件夹，并提示层号与记忆层级序数是否一致 |
| `检查 <工作区>` | 层级完整性检查：递归扫描，按记忆层级序数推断每处应有的记忆层，找出缺失的候选子模块/子工程 |
| `索引 [<工作区>] --层 记忆第X层 [--by 署名]` | 生成/更新该层 `记忆索引.json` 指纹档案（sha256+mtime+更新者；`--by` 省略时自动取本机配置 `agent_name`） |
| `校验 [<工作区>] --层 记忆第X层 [--refresh]` | 并发检测：报告自上次记录后被其他 Agent 改过/新增/删除的记忆文件；合并完成后用 `--refresh` 刷新指纹 |
| `刷新通用 <工作区> [--by 署名]` | 重建**所有** `记忆第X层/0_索引.md` 的「🔗 通用知识」段：保留已填摘要、补新增文件、删失效引用，并刷新受影响层指纹（§八·三 第 3 步的一键化） |
| `检索 <工作区> <关键词>` | 跨全部记忆层与 `记忆_通用` 全文检索，输出 `文件:行号:内容`（每文件最多 5 行）——层多时先检索再精读 |

> 署名小知识：本机 `~/.agent-tsg/config.json` 的 `agent_name` 字段由 scratchpad 技能的 `配置 --name` 写入，两个技能的工具共用——配置一次，两边留痕一致。

`工具/记忆助手.ps1` 是 Windows 薄封装（转发到 Python；用法 `.\工具\记忆助手.ps1 建层 <路径> --层 1`）。

**工具不是必须的**——没有 Python 时，按上面的协议手工读写也完全成立；指纹校验退化为「先读再改」的纪律。脚本细节见 `工具/README.md`。

## 七、与其他技能的联动

与 `cross-agent-scratchpad-skill`（临时脚本治理）是**共生关系**：本技能负责「理解和记录项目知识」，scratchpad 负责「临时脚本建在哪、能不能复用、何时删」。两者共用同一个接手任务入口，**一次深度阅读同时服务两者**；本技能的并发指纹保护思想也被 scratchpad 的 `manifests/index.json` 借鉴（保存前重读磁盘、原子写入）。

与 `cross-agent-dev-workflow-skill`（项目交付总流程）是**三位一体**关系：dev-workflow 掌舵（研发→测纠→整理发布三阶段 + 证据制验收门 + 停止闸），本技能是它的大脑——**它的阶段状态机就存在 `5_代办.md` 的「🚦 交付流程状态」段**，其各阶段的决策、踩坑、进度实时写入本技能各件（写入同样遵守「先读→合并→写回」）。联动细节见 `联动/cross-agent-dev-workflow.md`。

| 信息（scratchpad 产生） | 写入本技能的位置 | 说明 |
|---|---|---|
| 用户对临时脚本治理的偏好（保留期、命名、敢不敢删） | `3_个性化需求.md` | 用户亲口说的偏好是最高价值 |
| 「该工作区已完成遗留物审计 + 日期 + 结论」 | `1_项目架构.md` 末尾或 `5_代办.md` | 避免下一个 Agent 重复全量扫描 |
| 脚本相关的坑（路径失效、依赖冲突、必须在工作区跑等） | `2_踩坑日志.md` | 问题/原因/解决/影响 |
| 待迁移/待清理/待审计 | `5_代办.md` | 跨 Agent 接续任务 |
| quarantine 待用户拍板项 | `6_需要我配合.txt` | 按重要性排序 |
| 每次保留/迁移/删除的依据和结果 | `决策.md`（可选）+ scratchpad 库 `reports/` | 审计留痕 |

> **本机临时脚本库路径**（`~/.agent-tsg/config.json`）是设备级事实，**不放记忆**——跨设备不通用。联动约定详见 `联动/cross-agent-scratchpad.md`。

## 八、通用记忆（记忆_通用，跨层通用知识）

### 八·一、什么是「通用」

用户在对话中**明确标注**"这是通用的"/"跨项目都这样"/"不管哪个项目都按这个" → Agent 把这条知识写到 `<工作区>/记忆_通用/`，并**刷新所有 `记忆第X层/0_索引.md` 的「🔗 通用知识」段**。

**通用 vs 普通层的区别**：

| 维度 | 通用（`记忆_通用/`） | 普通层（`记忆第X层/`） |
|---|---|---|
| **位置** | 工作区根，与 `记忆第一层/` 平级 | 工作区任意层级的子目录里 |
| **可见范围** | **任何** `记忆第X层` 都能引用 | 仅本层 + 下层能引用 |
| **写入触发** | 用户明确说"通用" | Agent 按当前任务/项目需要 |
| **典型内容** | 跨项目的命名约定、注释风格、通用工具用法、通用踩坑 | 仅适用于本项目/本子模块的知识 |
| **更新方式** | 修改一次 → 刷新所有层 0_索引 引用 | 修改本层即可 |

### 八·二、文件夹结构

```
<工作区>/
├── 记忆_通用/                        ← 中央跨层通用知识（与 记忆第一层 平级）
│   ├── 0_通用索引.md                  ← 入口：所有通用知识的一句话摘要 + 直链
│   ├── 1_通用偏好.md                  ← 跨项目通用的命名/注释/字段偏好
│   ├── 2_通用配方.md                  ← 跨项目通用的提示词模板、工作流步骤
│   ├── 3_通用工具.md                  ← 跨项目通用的工具/脚本用法
│   ├── 4_通用踩坑.md                  ← 跨项目通用的易错点
│   └── 记忆索引.json
├── 记忆第一层/                       ← 普通层（0_索引 含「🔗 通用知识」段）
└── ...
```

### 八·三、用户说「这是通用的」时 Agent 必须做的步骤

1. **写入中央**：把内容写到 `<工作区>/记忆_通用/` 下对应文件（偏好 → `1_通用偏好.md`，配方 → `2_通用配方.md`，以此类推）。
2. **追加索引**：在 `0_通用索引.md` 加一条摘要直链。
3. **刷新所有层**：遍历工作区里**每一个** `记忆第X层/0_索引.md`，更新「🔗 通用知识」段的摘要（机械部分可一键完成：`python 工具\记忆管家.py 刷新通用 <工作区>`，摘要内容仍需 Agent 判断填写）。
4. **更新指纹**：跑 `python 工具\记忆管家.py 接手 <工作区> --by <署名>` 自动校验，或对 `记忆_通用` 执行 `索引 --层 记忆_通用`。

> **设计选择：中央 + 引用，不复制。** 遵守"一个事实一个出处"，避免同步漂移。**任何**层都能调用，因为 0_索引里都有引用，Agent 顺着引用跳过去就行。

### 八·四、建中央 记忆_通用

```powershell
python 工具\记忆管家.py 建层 <工作区> --通用
```

`接手` 命令每次会自动检测工作区有没有 `记忆_通用/`（[0] 段），缺则提示建一次。

## 九、路径可移植性规则（换电脑不丢记忆）

> ⚠️ **核心约束**：换电脑时你会**直接复制整个 AI 文件夹**（比如 `D:\AI\`）。所以记忆里**绝不能写死机器专属绝对路径**，否则复制到新电脑后所有路径都失效。

### 九·一、允许 / 禁止的路径写法

| 写法 | 示例 | 是否可用 |
|---|---|---|
| 占位符 `<工作区>` | `<工作区>/记忆_通用/1_通用偏好.md` | ✅ **推荐** |
| 相对路径（相对当前层文件夹） | `../../记忆_通用/0_通用索引.md` | ✅ 可用 |
| 相对路径（相对工作区根） | `记忆第一层/0_索引.md` | ✅ 可用 |
| 设备级配置（明确标注） | `~/.agent-tsg/config.json` | ✅ 可用（跨设备每台一份） |
| **机器专属绝对路径** | `D:\AAA实习\新闻爬虫\记忆第一层\` | ❌ **禁止** |
| **跨工作区绝对路径** | `D:\Oracle\SQL\脚本.sql` | ❌ **禁止** |

### 九·二、Agent 写入记忆时的纪律

1. 写到任何记忆文件前，先扫一遍有没有绝对路径 → **全部替换为占位符或相对路径**。
2. 引用别的记忆文件 → 用 `<工作区>/记忆第X层/xxx.md`（逻辑标识，深几层无所谓）。
3. 引用工作区**外**的资源（脚本、SQL、数据文件等）：**优先用逻辑标识**（如 `cross-agent-scratchpad` 的 `reusable/编码检测.py`）+ 在 `3_通用工具.md` 或本层 `3_个性化需求.md` 写明调用方式；**不要**写 `D:\临时脚本库\reusable\编码检测.py`。
4. 用户亲口说的本机路径（如"D 盘装 oracle"）→ 写到 `6_需要我配合.txt`（"需要我确认/补全路径"），**不**写进 `1_项目架构` 这种会被复制的记忆。

### 九·三、跨设备兼容：什么放记忆 vs 什么放本机配置

| 信息 | 放哪 | 跨设备 |
|---|---|---|
| 项目知识、踩坑、配方 | 记忆（嵌在工作区） | ✅ 工作区跟着复制走 |
| 通用偏好 | `<工作区>/记忆_通用/` | ✅ 同上 |
| **本机临时脚本库路径** | `~/.agent-tsg/config.json`（**不放记忆**） | ❌ 每台机器各配一份 |
| **当前用户名、操作系统** | 系统环境变量 | ❌ 跨设备会变 |
| **agent 署名** | `~/.agent-tsg/config.json` 的 `agent_name` | ⚠️ 共享，可不一样 |

## 强制使用的边界（诚实声明）

本 skill 通过协议强约束**加载了它的 Agent/Harness**。它无法从技术上强制未安装本 skill 的第三方工具遵守「先读→合并→写回」，也无法检测所有并发写入。为最大化覆盖：
- 已安装本 skill 的 Agent：每次任务必须走「读记忆/读项目 → 执行 → 更新记忆 → 层级完整性检查」全流程；
- `记忆索引.json` 指纹校验只能发现「上次记录之后」的改动，**不是强互斥锁**——最终靠协议纪律保证不覆盖；
- 模板（`_模板/`）只是格式参考，记忆的价值在于 Agent 深度理解后填写的真实内容；
- 「分几层」的判断由 Agent 深度研究后自主作出，工具只按「层号=记忆层级序数」做机械推断与校验，不做最终裁决。

## 关键原则

1. **就地嵌入**：记忆直接嵌在工作区的文件夹树里，随工作区走，不集中建独立库。
2. **层数研究出来，不是规定出来**：Agent 独立深度研究分析项目后自主定层，1~N 层不设上限；结论写进「分层方案」。
3. **层号 = 记忆层级序数**：根=第一层，路径上每多一个建了记忆层的祖先就 +1；分组文件夹不建层不占层号；跨 Agent 命名一致。
4. **深度理解后填写**：Agent 读懂项目、归纳总结后填 `0_索引` + 6 件，不是拷空模板。
5. **每次任务都用**：有记忆就更新，没有就阅读研究后定层添加。
6. **主动补齐**：结构变化/新增模块时（任意深度），按分层方案主动建对应记忆层，不等用户提醒。
7. **一个事实一个出处**：下层只写覆盖/补充并标注。
8. **写前三步，追加为主**：先读→合并→写回；条目带日期+署名；定期整理防膨胀。
9. **路径可移植**：记忆里只写 `<工作区>/xxx` 或相对路径，**绝不**写死机器专属绝对路径——换电脑复制 AI 文件夹时一切照常用。
10. **通用走中央**：用户明确说「通用」的知识写 `记忆_通用/`（中央+引用，不复制），刷新所有层的 0_索引 引用段。
